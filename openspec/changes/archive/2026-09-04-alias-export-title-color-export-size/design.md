## Context

`CatalogSyncService` (`Commands/CatalogSyncService.cs`) already has the exact shape a fifth "Aliases" section needs: `BuildExport()` calls each category's own `ExportNames()`-style method and appends it under a `## HEADER` via `AppendSection`; `ParseImport()` splits sections and calls `ImportPlainNames(lines, targetList, toCommand)` per category - a helper that already does dedup, line-sanity filtering, and sorting generically. Aliases (`config.Aliases.Titles/Outfits/Gestures/Restraints`, each a `List<...AliasDefinition>` with an `Alias` string field) has no owning "Command" class of its own to host an `ExportNames()`, but that's a minor placement detail, not a structural gap.

The Owner's "Alias / one-off" list (`config.QuickCommands.Aliases`, populated today only by `DrawFreeformComposer`'s manual "Add Command") is a plain `List<QuickCommand>` with no per-entry provenance (imported vs. hand-typed) - the same as Restraints' list, which already mixes manually-added entries (`collar/restraints`'s "Owner can add a restraint quick command by name") with imported ones and is already wiped wholesale by reset-imports today.

`GestureCommand.ExportCatalog()` (`Commands/GestureCommand.cs`) currently serializes the full `GestureCatalogEntry` (including `GroupSelections`, a `Dictionary<string, List<string>>`) as JSON, base64-encoded, per line. `CatalogSyncService.ImportGestureLines` (the only reader of this format) only ever accesses `entry.Id`, `entry.Label`, `entry.ModName`, `entry.GroupName`, `entry.GroupOrder`, `entry.OptionOrder` - confirmed by direct trace, no other field is read on import.

`TitleCommand.ForceApply(string text)` hard-codes `IsPrefix = false, Color = new(1,1,1)` - its own doc comment already flags this as incomplete ("No prefix/color control yet"). `ChatCommandListener.HandleForceTitle` dispatches on an exact-prefix match against `"create "` (with trailing space) and `"clear"` - title text itself is unstructured free text with no catalog to match against, unlike a restraint device name or a pairing keyword, so there's no way to append new syntax to `create` and have an old client fail closed the way other wire-format extensions in this plugin already do (see Goals below).

See proposal.md - Why for all three problems' full grounding (with exact file:line references) and What Changes for the shape of each fix.

## Goals / Non-Goals

**Goals:**
- Alias names reach the Owner through the exact same file/mechanism every other catalog already does - no new export/import UI, no new file format.
- The Gesture export shrinks by dropping only fields the importer already never reads - zero behavior change to how a Sub's own gestures play locally.
- The Owner's title color/prefix gap closes using controls and data shapes that already exist elsewhere in this codebase (the Sub's own `ColorEdit3`, `TitleAliasDefinition`'s `Color`/`IsPrefix` fields) - no new UI pattern invented.
- Any wire-format addition that can't degrade safely on an old client (see title, below) is a **new, distinct verb**, never an unsafe suffix on an existing free-text grammar.

**Non-Goals:**
- Per-entry provenance tracking (imported vs. manually-typed) for the Aliases quick-command list - reset-imports clearing the whole list, hand-typed entries included, is an accepted trade-off already made for Restraints; this change doesn't introduce new bookkeeping to change that for Aliases either.
- Migrating or re-encoding already-exported files - old exports still import fine; this only changes what a *newly generated* export contains.
- Touching Follow's alias words or the two singleton Clear-title/Unlock-outfit aliases - both already have dedicated fixed Owner quick-command rows, so exporting them via the new Aliases section would be redundant (see proposal.md's scope note).
- Redesigning the Gesture export's wire encoding (JSON+base64) itself - only trimming which fields go into that same encoding. A format change is a separate, larger decision this change doesn't make.

## Decisions

**Aliases export/import lives directly in `CatalogSyncService`, not a new "AliasCommand" class.** Unlike Wardrobe/Gesture/Moodles/Restraints, "Aliases" isn't a capability with its own apply/force-apply logic - it's a cross-cutting view over four existing `AliasBook` lists. A private `ExportAliasNames()` in `CatalogSyncService` (reading `config.Aliases.Titles/Outfits/Gestures/Restraints`, projecting `.Alias`, deduplicating case-insensitively, same as every other `ExportNames()` already does) is simplest and keeps the new section a peer of the other four rather than inventing a new owning class for four lines of logic.

**Import reuses `ImportPlainNames` unchanged**, with `toCommand: name => name` (the alias word *is* the command - no prefix like `outfit lock` or `moodle apply`, since an alias is resolved directly against the Sub's `ResolveAlias` dictionary, not through a reserved-category verb). This is exactly what typing the alias into the freeform "Alias / one-off" box already produces, so imported and hand-typed entries in that list are indistinguishable in shape - intentional, since the Owner should be able to Send/Remove either exactly the same way.

**Reset-imports adds Aliases to its cleared set**, moving it out of the "Title, Follow, Aliases" exclusion list in both the requirement text and `CollarWindow.cs`'s reset button and help-marker copy. This accepts the same trade-off already live for Restraints (a hand-typed one-off gets wiped along with imported aliases) rather than introducing new per-entry tracking - see Non-Goals.

**Gesture export gets a slimmed serialization shape, not a change to `GestureCatalogEntry` itself.** `GestureCatalogEntry` (the Sub's local catalog storage) keeps every field it has today, including `GroupSelections` - `Execute()` still needs it for local playback, looked up fresh from `LocalCatalog` by `Id` regardless of what any export ever contained. `ExportCatalog()` instead builds and serializes a small anonymous/record shape carrying only `Id`, `ModName`, `AnimationName`, `GroupName`, `GroupOrder`, `OptionOrder`, `Trigger` - `TryParseExport` deserializes that same shape. This keeps the local-catalog data model and gesture-playing code path completely untouched; only the export/import wire shape changes.

**Title color/prefix travels via a new `style` sub-verb, never a suffix on `create`.** Every other additive wire-format extension in this plugin (`restraint lock "<name>" rules:...`, `collarpair ... <triggerPhrase>`) fails closed on an old client because the *base* token being matched (a quoted name against a known catalog, or a keyword literal) still resolves correctly even if trailing syntax is ignored or a keyword simply isn't recognized. Title text has no such anchor - it's arbitrary free text, and `StripQuotes` (`text.Trim('"', '\'')`) only trims characters from the very edges of a string, not matched pairs, so any suffix appended after the text would corrupt an old client's plain-text `create` handling (verified by tracing `StripQuotes` against a hypothetical `"text" prefix:1 color:...` suffix - the trailing tokens survive into the applied title). A new verb (`title style "<text>" prefix:<0|1> color:<r>,<g>,<b>`), checked as its own branch in `HandleForceTitle` before/alongside `create`/`clear`, means an old client's exact-prefix dispatch simply falls through to "unrecognized title override" - a clean no-op, not corrupted title text. `create` itself is untouched and remains available (e.g. for a quick command someone doesn't want to bother styling).

**`QuickCommand` gains `TitleIsPrefix`/`TitleColor` fields**, mirroring the existing `GestureModName`-style "kept in sync with the encoded command" pattern (see that field's own doc comment) - these exist purely so the Owner's UI can display/reconstruct a title quick command's chosen style without re-parsing its own `Command` string; `Command` remains the actual source of truth sent over the wire.

## Risks / Trade-offs

- **A new title wire verb means mixed-version pairs can't use colored titles until both sides update.** → Accepted and disclosed (see proposal.md's "Known limitation, not a regression") - consistent with this plugin's existing convention (trigger-phrase auto-sync) that wire-format additions assume both sides update together; `create` keeps working unchanged in the meantime.
- **Reset-imports now also wipes hand-typed one-off Aliases entries**, which it didn't before. → This is a real, user-visible behavior change for anyone already using the freeform box - called out explicitly in the proposal and spec rather than silently absorbed; mitigated by the fact the exact same trade-off already exists for Restraints today, so it's not a new category of surprise for this Owner-tab feature area, just a wider application of an existing one.
- **Slimming the Gesture export payload is a one-way trim** - if some future need arose for the Owner side to know a specific mod-option's cross-group selection state, the field would need re-adding. → No current or foreseeable consumer needs it (confirmed by tracing every read site), and `GestureCatalogEntry`'s own local storage is untouched, so nothing is lost for the Sub - only what leaves their machine shrinks.

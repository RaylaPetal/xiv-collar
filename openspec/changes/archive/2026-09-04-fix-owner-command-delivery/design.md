## Context

See `proposal.md` - Why. Relevant current-state details (from direct code inspection of the reported session):

- **`TriggerPhrase` is a bare per-client `PluginConfig` field** (`public string TriggerPhrase { get; set; } = "command";`), read independently by two unrelated code paths: `ChatComposer.Wrap` (the SENDING side, uses ITS OWN local value to build outgoing text) and `ChatCommandListener.OnChatMessage` (the RECEIVING side, uses ITS OWN local value via `text.StartsWith(trigger)` to recognize incoming text). Nothing ever transmits or compares these two independently-configured values - if a Sub changes theirs (as the reported Sub did, to "ray") without the Owner separately changing their own copy to match, the Owner's composer keeps producing tells starting with "command", which the Sub's `text.StartsWith(trigger)` check (`trigger` = "ray") always rejects before ever reaching `Resolve()`. This silently affects every category the reserved-word/alias dispatch covers (title, outfit, gesture, collar, moodle, restraint) - the discarded message produces no feedback of any kind, which is why every one of "no titles apply", "no outfits apply", "collar unlock kept my neck slot locked" traces back to this one root cause once you check each category's Owner-tell path and find it always starts with the same `OnChatMessage` gate.
- **The pairing handshake already transmits and captures `PeerName`/`PeerWorld`** via `TryHandlePairingMessage`/`AcceptPending`/`PairingCommand.AcceptPeer`, from a `collarpair <role> <code>` tell parsed with `SplitFirstToken` (first-space split). This is the existing, proven mechanism for one side learning something about the other during the one-time handshake - trigger phrase can piggyback on the exact same message and flow.
- **`GestureCatalogScanner.BuildIndex()`** builds its emote-command index from `Plugin.DataManager.GetExcelSheet<Emote>()`, filtering only on `emote.TextCommand.IsValid` (the row reference resolves) before extracting `command = emote.TextCommand.Value.Command.ExtractText().TrimStart('/')` - it never checks whether the extracted `command` string is actually non-empty. `Lookup()`'s `hits.FirstOrDefault(...).Command` returns this same (possibly empty) string when a path match is found, and `GestureTriggerResolver.Detect`'s `is { } cmd` pattern only excludes `null`, not empty string - so a matching entry with blank command text still becomes `Add(new GestureTrigger { Kind = SlashCommand, SlashCommand = "" })`, cataloged as "playable." Played via `GestureCommand.Play`/`RestraintCommand`'s reused copy, this produces `Chat.SendMessage("/ motion")` (an empty command with `TrimStart('/')` applied), which the game rejects exactly as observed: `The command / motion does not exist.`
- **Every other Owner-force path was audited and found clean**: `TitleCommand.ForceApply` (Honorific IPC only), `OutfitCommand.ForceApply` (Glamourer IPC + `SlotLockManager` only), `CollarCommand.ForceApply` (`SlotLockManager` only), and `MoodlesCommand.ForceApply` (Moodles IPC only) never call anything chat-related - each is gated solely by `OnChatMessage`'s trigger-phrase check before `Resolve()` runs. No separate bug exists in any of these four; the trigger-phrase fix is a complete fix for them.
- **`PenumbraIpc.TrySetTemporarySettings`/`TryRedrawLocalPlayer`/`TryGetLocalPlayerCollectionId`** each only log on a thrown exception (`catch (Exception ex) { Plugin.Log.Error(...) }` or a bare `catch { return null/false; }` with no logging at all) - a documented non-success `PenumbraApiEc` return value (per the Penumbra.Api XML docs: `ModMissing`, `OptionGroupMissing`, `OptionMissing`, `TemporarySettingImpossible`, `TemporarySettingDisallowed`, `CollectionMissing`) is swallowed into a plain `false` with zero diagnostic trail. `collar/gesture`'s existing "Temporary activation fails... reports the failure" requirement is therefore only partially met (exceptions only), which is why the "only plays if already enabled" report can't be conclusively diagnosed from today's logs - this fix is a prerequisite for actually root-causing that remaining symptom, not a guaranteed fix of it by itself.
- **A live report contradicted the "manual typing" theory for the outfit case**: a *correctly formed* `/tell` (right trigger phrase, right grammar) sent by the Owner and received by the Sub still produced `The command /outfit lock kagome does not exist.` on the Sub's own screen, with duplicate plugin installs and missing permissions/ToS both independently ruled out by the reporter. `ChatCommandListener.OnChatMessage` is registered purely as an observer of Dalamud's `IChatGui.ChatMessage` event and never calls `Chat.SendMessage`, `ProcessChatBoxEntry`, or any other command-execution API on the receiving side - there is no line of code in this repository that could produce this specific symptom. Every decision point in `OnChatMessage`/`Resolve`/`HandleForce*` is silent today (no logging at all), which is why this took two full rounds of manual transcript reconstruction to even narrow down this far, and still couldn't be conclusively resolved from code alone.

## Goals / Non-Goals

**Goals:**
- Make the trigger phrase self-synchronizing across a pairing, so it can never again silently diverge between an Owner and Sub who paired with each other.
- Make a paired Owner able to see, in Settings, which trigger phrase is actually being used for the peer they're paired with.
- Stop cataloging gesture triggers that can never actually execute (blank slash-command text).
- Make every gesture temporary-activation failure path (not just exceptions) log enough detail to diagnose from a log file.
- Make the entire receive-and-dispatch pipeline for an incoming trigger tell locally diagnosable, so an unexplained "it didn't work" report next time is a five-minute log read instead of a multi-session transcript reconstruction.
- Let a Sub test an Owner-style command's full dispatch path (trigger phrase, permissions, reserved-word/alias matching) entirely locally, with no peer, no pairing, and no chat message sent or received.

**Non-Goals:**
- Redesigning the trigger-phrase/reserved-word command grammar itself (`title`/`outfit`/`gesture`/`collar`/`moodle`/`restraint` stay reserved words after a trigger phrase, unchanged).
- Fully resolving the "gesture only plays if already enabled" report end-to-end in this change - the logging fix is a necessary diagnostic prerequisite; if it surfaces a further concrete defect once reproducible with real log output, that's follow-up work, not scope creep into this change.
- Changing how pairing identity itself is verified (still the server-verified sender name+world, unchanged) - trigger phrase is additional convenience data riding the same handshake message, not a security/consent mechanism.

## Decisions

### 1. Trigger phrase rides the existing pairing handshake message, additively
`ComposePairing()` appends this client's own current `TriggerPhrase` as a trailing segment: `collarpair <role> <code> <triggerPhrase>`. `TryHandlePairingMessage` parses it with one more `SplitFirstToken` split (role, then code-and-rest, then code, then trigger phrase = whatever remains, trimmed - empty if absent). `PendingPairingRequest` gains a `TriggerPhrase` field carrying it through to `AcceptPending`, which passes it to a widened `PairingCommand.AcceptPeer(name, world, triggerPhrase)` that stores it in a new `PairingState.PeerTriggerPhrase`.

**Alternative considered**: a separate dedicated handshake message just for trigger-phrase exchange. Rejected - the existing handshake is already the one-time, code-gated moment both sides confirm identity; piggybacking avoids a second round-trip and a second place that can be skipped or done out of order.

### 2. Composing uses the peer's captured phrase, falling back to the local one
`ChatComposer.Wrap` changes from unconditionally reading `config.TriggerPhrase` to `config.Pairing.PeerTriggerPhrase is { Length: > 0 } peerPhrase ? peerPhrase : config.TriggerPhrase`. This makes the fix retroactive-safe: an existing pairing with no captured peer phrase (formed before this change, or with a peer who hasn't updated) keeps exactly today's manual-matching behavior rather than breaking outright.

### 3. Settings surfaces the phrase actually in effect
A small read-only line in Settings' Identity & Pairing card (where pairing state already renders) shows "Trigger phrase in effect: `<phrase>`" using the same fallback logic as decision 2, with a visible distinction between "from your paired Sub" and "your own (peer hasn't sent theirs)" - giving a paired Owner a way to actually notice a mismatch instead of it being invisible.

### 4. Gesture catalog: reject blank command text at detection time, not at play time
`GestureTriggerResolver.Detect`'s `Add` call for the redirected-path/`Lookup` case changes its guard from `Lookup(path[..^4]) is { } cmd` to `Lookup(path[..^4]) is { Length: > 0 } cmd`, so an emote with blank `TextCommand` text is treated identically to "no match found" (falls through to non-playable, per the existing "Option has no playable trigger" requirement) rather than being cataloged as a false-positive playable trigger.

### 5. Log every non-success Penumbra EC, not only exceptions
`PenumbraIpc.TrySetTemporarySettings`/`TryRedrawLocalPlayer`/`TryGetLocalPlayerCollectionId` each gain a `Plugin.Log.Warning` (or `.Error` for the redraw/collection lookup, matching existing severity conventions in this file) on a non-success return value from the underlying IPC call, including the specific `PenumbraApiEc`/failure detail, mirroring the detail already captured on the exception path.

### 6. `Resolve`/`HandleForce*` change from `void` to returning a shared `CommandOutcome`, logged at `Information` level
A small `readonly record struct CommandOutcome(bool Success, string Message)` replaces every `HandleForce*` method's `void` return and `Resolve`'s own `void`. Each branch that previously just called a `Command.ForceApply`/etc. and discarded the bool now wraps it in a message (`"Outfit \"kagome\" applied."` / `"No wardrobe design named \"kagome\"."` / `"Outfit permission not enabled."`), and the permission/ToS gate in `Resolve`'s `switch` returns a `Fail` outcome instead of silently `return`-ing. `OnChatMessage` captures the outcome from `Resolve(alias)` (previously fire-and-forget) and logs `Plugin.Log.Information($"Trigger tell dispatch: {outcome.Message}")`, plus separate `Information` lines for a sender/world mismatch and a trigger-phrase mismatch (the two checks that happen *before* `Resolve` is ever called). `Information` matches this codebase's existing, apparently deliberate convention (checked: every `Plugin.Log` call site today is `Information`, `Warning`, or `Error` - none use `Debug`/`Verbose`), including the one existing precedent for exactly this kind of message (`HandleForceRestraint`'s "Unrecognized... override" line, already `Information`). Using the established level means the trace is visible in Dalamud's default log view without the reporter needing to first discover and change a log-level setting. Every line stays purely local (`Plugin.Log`, Dalamud's own log sink) - nothing is added to any chat-composing or chat-sending path. Only messages that reach `OnChatMessage` as a `TellIncoming` at all are candidates for these lines, keeping volume in line with how many tells the Sub actually receives, not general chat traffic.

### 7. Local test tool reuses the exact same `Resolve`/`CommandOutcome` path
`ChatCommandListener` gains `public LocalTestResult TestIncomingCommand(string rawText)`: it checks `rawText.TrimStart().StartsWith(config.TriggerPhrase, OrdinalIgnoreCase)` itself (the one check `Resolve` doesn't do, since real incoming tells have that checked by `OnChatMessage` before `Resolve` is reached) and, if it matches, strips the trigger and calls the *exact same* `Resolve(alias)` used for real tells - reusing decision 6's `CommandOutcome` return value directly, mapped to `LocalTestResult.Ok`/`Fail`. This is deliberately not a separate, parallel implementation of the dispatch logic (which could drift from the real path and stop being a reliable test) - it is the real path, called directly, minus the sender-identity check (which requires a real verified sender that a local test can't have) and the tell-channel-type check (irrelevant to a text box). A small "Test an Owner command" control (text input + run button) is added near Settings' Identity & Pairing card, reporting the result the same way existing `collar/ui-organization` local Test controls do.

**Alternative considered**: a fully separate "dry run" mode that reports what *would* happen without actually applying anything. Rejected - `collar/ui-organization`'s existing local Test controls already establish the precedent that a local test actually executes the action (so the Sub can visually confirm it), and a dry-run mode would require a second, parallel code path through every `Command.ForceApply` that could itself drift out of sync with the real one - the opposite of what a trustworthy test tool needs.

## Risks / Trade-offs

- **[Risk]** Appending a segment to the handshake message text is a wire-format change to `collarpair`. → Mitigation: purely additive and positioned last, parsed via "whatever remains after the code" - an old client's parser (which only ever looked at `roleToken`/`receivedCode` via one `SplitFirstToken` split) would fold the trigger phrase into what it treats as the code, which no longer matches its own generated code and fails the equality check, silently ignoring the handshake exactly like a malformed one today (`TryHandlePairingMessage` already treats a wrong/malformed code as "ignore, never falls through"). Both sides must actually update for the fix to take effect; a mixed old/new pairing regresses to today's manual-matching behavior, not a crash or a worse failure mode.
- **[Risk]** The gesture logging fix could be noisy if a stale/removed mod produces frequent temporary-activation failures. → Mitigation: this only logs on an actual failed attempt (an Owner/Sub-triggered gesture play), the same frequency exceptions already log at today - not a new noise source, just a previously-silent one made visible.
- **[Trade-off]** This change does not itself prove or disprove the deeper "only plays if already enabled" hypothesis - it only makes the next real occurrence diagnosable. Accepted since reproducing and root-causing it further needs live logs from an actual failing session, which isn't available while writing this proposal.

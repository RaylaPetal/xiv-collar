## Why

A real paired Owner/Sub session reported that almost no Owner command works: titles don't apply, outfits don't lock, collar unlock doesn't release the Neck slot, and gestures fire inconsistently with visible `The command /X does not exist.` errors. Tracing the actual code (not just the symptom) found the dominant root cause: the trigger phrase that must prefix every command tell is a purely local, per-client setting with no way for the two sides to ever discover or confirm they match. The Owner's composer always uses their own local trigger phrase; the Sub's listener only recognizes messages starting with its own local trigger phrase. If a Sub sets theirs to something other than the default ("ray" in the reported case) and the Owner never separately sets their own copy to match, literally every category of Owner-issued command is silently discarded by the Sub's listener - with no visible symptom pointing at the actual cause, since a discarded tell produces no error at all (unlike the misleading "/X does not exist" lines the Owner and Sub triggered by hand-typing raw text fragments while troubleshooting).

Two secondary, independently-verified bugs compound the confusion around gestures specifically: some cataloged gestures resolve to a slash-command trigger with an empty command string (from an FFXIV emote whose text-command data is blank despite otherwise being a valid row), producing a literal `/ motion` submission that always fails; and Penumbra IPC failures during gesture temporary activation are only logged when the call throws, not when it returns a documented non-success result code, making the already-specified "reports the failure" requirement (`collar/gesture`) impossible to actually diagnose from logs.

**Coverage - every Owner-tell category was individually audited, not just outfit/gesture:** `TitleCommand`, `OutfitCommand`, `CollarCommand`, and `MoodlesCommand`'s Owner-force paths call only their respective IPC (Honorific/Glamourer/SlotLockManager/Moodles) and never touch chat at all - each is gated *exclusively* by `ChatCommandListener.OnChatMessage`'s trigger-phrase check before `Resolve()` ever runs. That means the trigger-phrase fix alone is a complete fix for all four categories' "doesn't work via the Owner tab" symptom - there is no other code in any of those four command classes that could be silently failing. `GestureCommand` and `RestraintCommand` sit behind the same gate and additionally get the two gesture-specific fixes below (restraints reuse `GestureCommand.Play` for their bound-animation rules, so the ghost-trigger fix covers both).

**On the `ray outfit lock kagome` report, revised**: this was confirmed to be a *correctly formed* command (right trigger phrase, right grammar), typed and sent by the Owner as a normal `/tell`, received by the Sub - who then saw `The command /outfit lock kagome does not exist.` on their own screen. With duplicate plugin installs and missing Sub-side permissions/ToS both ruled out, this cannot be explained by any code path in this repository: `ChatCommandListener.OnChatMessage` only *observes* an incoming tell (via Dalamud's `IChatGui.ChatMessage` event) and never calls anything that submits text to the game's own command processor - there is no line of code anywhere in this plugin that could construct or execute `/outfit lock kagome` as a real slash command on the receiving side. Rather than propose another speculative fix for a mechanism that isn't in this codebase, this change adds trace-level logging across the entire receive-and-dispatch pipeline (see "Diagnostic logging" below) so the next occurrence is actually diagnosable from the Dalamud log instead of requiring another round of manual transcript reconstruction.

## Diagnostic logging (new, in response to the still-unexplained outfit case)

`ChatCommandListener.OnChatMessage`/`Resolve` and every `HandleForce*` method currently make several silent decisions with zero logging: message type filtered out, sender mismatch, trigger-phrase mismatch, permission/ToS gate, reserved-word dispatch, unrecognized alias, and each `Command.ForceApply`'s own match-by-name failure. None of these log anything today, which is exactly why two full rounds of transcript archaeology were needed to get this far. Adding a trace log line at each decision point (only active for tells that at least reach `OnChatMessage`, so this doesn't spam unrelated chat) turns every one of these silent branches into a one-line, timestamped answer to "why didn't this apply" - including, crucially, the possibility that something *outside this plugin* is responsible (if the log shows this plugin never even received/matched the message, that's conclusive evidence to look elsewhere, e.g. another installed plugin intercepting chat).

## Local Owner-command test tool (new, requested directly)

Every round of this debugging saga required an actual paired peer to send a real tell, then reconstructing what happened from a chat transcript. A Sub SHALL be able to test an Owner-style command entirely locally - typing the exact raw text an Owner would send (trigger phrase included) into a dedicated control and getting an immediate, specific pass/fail result - without pairing, without a real sender, and without sending or receiving any chat message. This exercises the *exact same* trigger-phrase check, permission/ToS gates, and reserved-word/alias dispatch logic a real incoming tell goes through (the one thing this whole investigation could never directly observe), with the one deliberate difference being that no real sender identity is checked, since there is no real sender in a local test. This is a different, complementary tool to the existing per-action "Test" buttons (`collar/ui-organization`): those exercise one action's own local effect directly, bypassing the command-text parsing entirely; this tool exercises the parsing itself, which is exactly where every bug in this change was found.

## What Changes

- The pairing handshake message SHALL additionally carry the sender's own configured trigger phrase, and the receiving side SHALL store it as the peer's trigger phrase upon accepting. **BREAKING** in the narrow sense that a handshake between one updated and one un-updated client falls back to the old manual-matching behavior (graceful degradation, not a hard failure) rather than syncing - both sides should update together for it to actually resolve the bug.
- Composing an outgoing command tell to a paired peer SHALL use that peer's stored trigger phrase (learned from the handshake) instead of the composing side's own independently-configured trigger phrase, so the two can never again silently diverge for an already-paired relationship.
- The Settings UI SHALL make clear, once paired, which trigger phrase is actually being used to compose outgoing tells, so a mismatch (e.g., from an un-updated peer) is visible rather than silent.
- Gesture cataloging SHALL exclude a resolved slash-command trigger whose command text is empty or whitespace - such an entry is not actually playable and must not be offered as one.
- Gesture temporary-activation failures (Penumbra reporting a non-success result, not only a thrown exception) SHALL be logged with the specific failure reason, matching the detail already logged for exceptions - fixing an existing `collar/gesture` requirement ("reports the failure") that the implementation doesn't fully satisfy today.
- Every stage of receiving and dispatching an incoming trigger tell (sender match, trigger-phrase match, permission/ToS gate, reserved-word or alias dispatch, and the resulting apply/failure) SHALL be logged locally with enough detail to determine why a command did or did not apply, without transmitting anything to the Owner or anyone else.
- A Sub SHALL be able to type raw command text (as if it were an incoming trigger tell, trigger phrase included) into a local control and get an immediate, specific result - without pairing, without a real sender, and without sending or receiving any chat message - exercising the same trigger-phrase, permission/ToS, and dispatch logic a real tell goes through.

## Capabilities

### New Capabilities
(none — all changes extend existing capabilities)

### Modified Capabilities
- `collar/pairing`: the handshake message additionally carries and captures the sender's trigger phrase alongside role and code.
- `collar/chat-transport`: composing a trigger message to a paired peer uses that peer's captured trigger phrase rather than the composing side's own independently-configured value; receiving and dispatching an incoming trigger tell is now locally diagnosable end to end, and can be exercised entirely locally via a new test control.
- `collar/gesture`: a resolved slash-command trigger must carry non-empty command text to count as a playable, cataloged trigger.

## Impact

- `CollarSystem.Plugin/Config/PluginConfig.cs` — `PairingState` gains `PeerTriggerPhrase`.
- `CollarSystem.Plugin/Commands/ChatCommandListener.cs` — `PendingPairingRequest` carries the sender's declared trigger phrase; `TryHandlePairingMessage` parses it from the handshake text; `AcceptPending` passes it to `PairingCommand.AcceptPeer`.
- `CollarSystem.Plugin/Commands/PairingCommand.cs` — `AcceptPeer` takes and stores the peer's trigger phrase.
- `CollarSystem.Plugin/Commands/ChatComposer.cs` — `ComposePairing` includes this client's own trigger phrase; `Wrap` uses `Pairing.PeerTriggerPhrase` when set, falling back to `config.TriggerPhrase` only when it isn't (pre-handshake, or an un-updated peer).
- `CollarSystem.Plugin/UI/SettingsWindow.cs` — surface which trigger phrase is actually in effect for the current pairing.
- `CollarSystem.Plugin/Commands/GestureCatalogScanner.cs` — `BuildIndex()` skips an emote whose extracted `TextCommand` text is blank.
- `CollarSystem.Plugin/Ipc/PenumbraIpc.cs` and/or `CollarSystem.Plugin/Commands/GestureCommand.cs` — log the specific non-success result when temporary-activation IPC calls fail without throwing.
- `CollarSystem.Plugin/Commands/ChatCommandListener.cs` — add trace logging at every decision point in `OnChatMessage`/`Resolve`/each `HandleForce*` method (message received, sender check, trigger check, permission/ToS gate, dispatch outcome); `Resolve`/`HandleForce*` change from `void` to returning a small outcome describing what happened, reused by both the logging and the new local test tool; a new `TestIncomingCommand(string rawText)` entry point reuses this same outcome for the UI.
- `CollarSystem.Plugin/UI/SettingsWindow.cs` (or `CollarWindow.cs`'s Owner tab) — a new "Test an Owner command" control: a text input plus a run button, reporting the result the same way existing local Test controls do (`collar/ui-organization`).

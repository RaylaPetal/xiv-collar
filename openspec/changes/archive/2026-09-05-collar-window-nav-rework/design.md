## Context

See `proposal.md` for motivation. `CollarWindow.cs` currently has a flat `NavItems` array (9 entries) and a `Draw()` switch that calls one `Draw*Module` method per Sub-authoring tab, plus a single `DrawOwnerModule` that internally stacks 8 independently-collapsible accordions (`DrawOwnerSection`) covering every category, with catalog sync/import/reset at the top. `activeModule` (the selected tab id) is in-memory only, not persisted in `PluginConfig` - so relabeling or restructuring tab ids has no save-data migration to worry about. `CollarWindow.OpenOwnerTab()` is the one external hook that jumps straight to the old Owner tab, called from the favorites quick-access menu; removing that menu entry (per the modified "Compact favorites window..." requirement) makes this method dead code.

## Goals / Non-Goals

**Goals:**
- One tab per shared category, content role-aware, so the nav bar's visual weight matches what each role actually uses.
- Preserve every existing operation (add, import, compose, copy, send, scan, favorite) exactly as it behaves today - this is a reorganization and relabeling, not a functional rewrite.
- Keep the `gesture` wire keyword and all config/field names untouched - only display text changes.

**Non-Goals:**
- Redesigning Settings' Identity & Pairing or ToS tabs - unaffected beyond the "Scanning" tab's removal (see Decisions). The four per-category scan bodies keep their own internal layout and "Wardrobe design allowlist & scan" label verbatim; only which window renders them changes.
- Changing `QuickCommands`/`AliasBook`/`PluginConfig` data shape - this stays a UI-layer change.
- Deciding whether the favorites bar becomes the Owner's primary daily-use surface - a separate, larger question raised during exploration but not part of this change.

## Decisions

**Role-aware content lives behind the existing per-category `Draw*Module`/`Draw*QuickSection` methods, dispatched from one tab.** For each shared category, the tab's render function becomes: `if (config.Role == PluginRole.Sub) Draw<Category>Module(); else { canSend = ...; Draw<Category>QuickSection(canSend); }`. This reuses each method's existing body near-verbatim - the change is almost entirely about *where* they're called from (their own tab vs. an accordion inside "owner"), not rewriting their internals.

**No cross-role preview.** `DrawOwnerModule`'s old "Owner UI preview: you are configured as Sub" banner let a Sub inspect the Owner accordion without changing Role, since it lived on its own dedicated tab reachable regardless of Role. That capability was never captured by any spec (the words "preview" appears in no `openspec/specs/` file) - it was a debugging convenience noted only in a code comment. Once each shared tab strictly shows the view for the *current* Role, there is no separate "Owner tab" left to preview from, and adding a manual per-tab preview toggle would be new, unspecified scope. This design drops it: switching Role in Settings is the only way to see the other view, matching exactly what the ui-organization delta's "Category tabs present role-aware content" requirement says. The still-relevant "No /tell target yet" warning (about pairing state, not Role) is kept, shown at the top of every shared tab's Owner-role view via a small shared helper instead of being computed once in `DrawOwnerModule`.

**`NavItems` shrinks from 9 flat entries to 10 restructured ones** (Title, Outfit, Animation, Moodles, Restraints, Custom Triggers, Collar, Follow/Leash, Permissions, Sync) - one more than today's 9 because Collar/Follow splits into two. No entry is removed outright; "Owner" as a distinct nav destination goes away, its categories redistributed into the shared tabs, and its sync/import controls move to the new Sync tab.

**Collar tab splits its existing body.** `DrawCollarModule`'s existing collar-item/Moodle section and its existing "Leash triggers" section (currently both drawn top-to-bottom in one method) become two methods, one per new tab, with no change to either section's own controls.

**Sync tab reuses `DrawCatalogRelaySection` and `DrawImportCommandsButton` near-verbatim**, just called from their own tab instead of the top of `DrawOwnerModule`.

**Sync tab's Sub-role view carries scanning and export, not just an explanation - Settings' "Scanning" tab is gone entirely.** The original plan gave Sub an inert message pointing at Settings' "Scan & Export" card, then a follow-up moved just the Export action there. Both undersold it: once catalog sync had its own tab, leaving scanning behind in Settings split one workflow (scan, then export) across two windows for no reason, and read as an oversight rather than a decision. `DrawScanAndExportCard` (the "Scan all" button), `DrawWardrobeScanBody`/`Feedback`, `DrawGestureScanBody`/`Feedback`, `DrawRestraintScanBody`, `DrawMoodlesScanBody`/`Feedback`, `DrawPenumbraFolderPicker`, `ParentFolders`, and `DrawAllowlistBody` all moved verbatim from `SettingsWindow` into `CollarWindow`, called in sequence from `DrawSubExportSection` before the Export button; their three backing fields (`gestureModSearch`, `penumbraFolderSearch`, `newWardrobeAllowlistFolder`) moved with them. `DrawTestButton` stayed in `SettingsWindow` - it's shared with "Test an Owner command," unrelated to scanning. Settings' internal tab bar drops its "Scanning" tab entirely, leaving Identity & Pairing and ToS. This revises the "Sync tab holds catalog relay sync and import/reset" requirement's Sub scenario; see the updated spec delta.

**"Reset imports" now also clears the browsable Animation/Restraints catalogs.** Verifying the Sync tab's Import flow surfaced that `RemoveImportedEntries` (Reset imports' handler) only ever cleared the imported *quick-command lists* (`quick.Titles`/`Outfits`/`Gestures`/`Moodles`/`Restraints`), never `GestureMapping.ImportedPeerCatalog` or `RestraintMapping.ImportedPeerCatalog` - the dictionaries the Owner's mod-browser dropdowns actually read from. Combined with the missing `Clear()` fixed above, a Restraints (or Animation) entry imported before that fix had no way to be purged short of a fresh import overwriting it, even via "Reset imports," which looked like it should have. Added `.Clear()` on both dictionaries to the Reset imports handler so a stale entry can always be cleared immediately without needing a new import file on hand.

**Empty Owner quick-command lists link to Sync instead of naming a location that moved.** `DrawOutfitQuickSection`/`DrawGestureQuickSection`/`DrawMoodlesQuickSection` used to say "use \"Import commands\" above" back when Import commands was the top of the same Owner accordion these lists lived in. Now that it's a separate tab, "above" is simply wrong. A shared `DrawGoToSyncTabPrompt` helper replaces the stale text with a button that sets `activeModule = "sync"` directly - CollarWindow already owns `activeModule`, so this needed no new plumbing.

**Fixed, not just relocated: restraint catalog import didn't clear before merging.** While verifying the Sync tab's Owner-role Import flow, a pre-existing bug surfaced: `CatalogSyncService.ParseImport` clears `stagedGestureCatalog` before repopulating it on a refreshed Gesture section, but the equivalent `stagedRestraintCatalog.Clear()` was missing for Restraints, so re-importing only ever added entries and never dropped ones the new export no longer carried - surfacing as the same mod appearing twice once its catalog id had reason to change. Fixed by adding the missing `Clear()` under the same `restraintCatalogRefreshed` gate already used to decide whether to write to the catalog at all. Unrelated to the nav rework itself, but found by exercising it and cheap to fix in the same change.

**Animation/Outfit renames touch only string literals**, not identifiers: `NavItems`' tooltip strings, `IconGlyph.Text(...)` title arguments, the Permissions checkbox label, and any other `ImGui.*`-visible text. `GestureCatalogEntry`, `GestureCommand`, `DrawGestureModule`/`DrawGestureQuickSection`, `QuickCommands.Gestures`, `permissions.Gesture`, and `ChatCommandListener.ReservedCategoryWords`'s `"gesture"` entry are all left exactly as they are - this is deliberately a display-only rename, not a rename of the capability or its wire behavior (see proposal.md's Impact section and the new "Animation category naming..." requirement's wire-compatibility scenario).

**`OpenOwnerTab()` is removed, not repurposed.** With "Open Owner commands" gone from the favorites menu (per the modified "Compact favorites window..." requirement) and every shared tab already Owner-aware via Role, there's no remaining caller and no remaining destination for it to jump to that "open the main window" doesn't already cover.

## Risks / Trade-offs

- [Reusing existing Draw* method bodies risks silently changing an existing operation while relocating it] -> each category's existing method keeps its own signature and internal logic untouched; only its call site changes, and tasks.md should verify each category's full operation set (add/import/compose/copy/send/scan/favorite as applicable) still works identically post-move.
- [A user with muscle memory for the current 9-tab layout, especially the far-right "Owner" tab, has to relearn the nav] -> one-time adjustment; the new layout is intended to make the common case (Owner only ever needing their own categories, Sub only ever needing theirs) faster, not slower, once learned.
- [Splitting Collar/Follow could be read as removing functionality if someone lands on "Collar" expecting leash controls still there] -> the new "Follow / Leash" tab sits immediately adjacent to "Collar" in the nav order, and both tabs' icons/labels make the split legible at a glance.
- [Renaming "Gesture" to "Animation" in the Permissions checkbox changes visible text a returning user has scanned past for versions] -> the underlying behavior and permission semantics are completely unchanged, only the label; the help-marker text next to it can call out "(previously labeled Gesture)" for one release if that reads as valuable, though this isn't required by the spec above.

## Migration Plan

Purely a UI-layer change with no persisted-state migration: `activeModule` is in-memory only, and no `PluginConfig` field encodes a tab id, category name, or the old "Gesture"/"Wardrobe" strings anywhere that needs converting. Ship as a single release; nothing needs a compatibility shim on either side of a paired Owner/Sub, since the wire-level `gesture` keyword and all reserved words are untouched. Rollback, if needed, is a plain revert - there's no data format to unwind.
